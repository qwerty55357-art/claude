# «Раскрой» — история сессии (для продолжения в Cowork)

Дата фиксации: 2 сентября 2026. Эта сессия шла поверх многомесячной многосессионной разработки калькулятора раскроя стеновых панелей — здесь только то, что сделано **в этом разговоре**, начиная с состояния «есть раскрой, откосы, LED, ручная корректировка карты, верстак, per-segment стыки уже частично» и заканчивая текущим зафиксированным чекпойнтом.

## Где что лежит

- **Рабочий файл:** `/mnt/user-data/outputs/raskroy.html` — актуальная версия, продолжать редактировать её.
- **Зафиксированный чекпойнт:** `/mnt/user-data/outputs/raskroy_checkpoint_2026-09-02.html` — идентичная копия на момент явной фиксации версии (по просьбе пользователя, «дальше будут правки, но пока возьмём эту версию»). Если что-то в новой правке пойдёт не так — сравнивать с ним.
- **Тестовая инфраструктура** (`audit.js`) — приложен к этому же сообщению отдельным файлом. Это не часть самого приложения, а автономный Node-скрипт для стресс-теста расчётного ядра на случайных сценах. Держать рядом с проектом, гонять после каждой правки расчёта.

## Архитектура (не менялась в этой сессии, но обсуждалась явно)

Однофайловый HTML без бэкенда: `<style>` (142 строки, 14 CSS-переменных, ими управляется вся палитра) + `<script>` (~2440 строк). Внутри script три естественно разделённых слоя:

1. **Вычислительное ядро** (~955 строк, ровно те функции, что перечислены ниже) — **полностью чистое от DOM**, ни одного обращения к `document`/`window`/`querySelector`. Это специально проверено: `subRanges, subIn, buildLayout, packSheets, packSheetsCols, buildOtkosParts, packOtkos, nestProfile, subtractRects, holeRects, applyManual, wallS, jointSegKey, jointSegMode, otkosMode, computeProject, compute`, плюс данные `PRESETS`.
2. **Отрисовка** — 13 функций `render*` (renderCards, renderScheme, renderCutmap, renderSpec, renderEstimate, renderNotes, renderOpenings, renderSeams, renderJointsV, renderLedSummary, renderShelf, renderWallTabs, renderCuts). Читают CSS-переменные, не хардкодят цвета (кроме 5 цветов материалов в объекте `MATCOLORS` — единственное исключение).
3. **Управление** — два больших IIFE-блока (drag/клик/меню на схеме стены и на карте раскроя) + обработчики форм.

**Как тестировать ядро отдельно (рецепт, использовался весь разговор):** ядро вырезается из `raskroy.html` python-скриптом (ищет `function <имя>(` и парную закрывающую скобку по балансу `{}`) и собирается в `core.js` с `module.exports`. Дальше — обычный `node -e "..."` или Node-тесты. Точный скрипт-экстрактор — в конце этого файла, раздел «Рецепт пересборки core.js».

**Аудит** (`audit.js`, отдельный файл) — генерирует 12 000 случайных стен (случайные проёмы, случайные режимы стыков/откосов, мультистены, материалы заполнения) и гоняет ~40 инвариантов (L1…L72): деталь в листе, без пересечений, сумма площадей сходится, число деталей откоса совпадает с ожидаемым, ни один кусок не длиннее листа, и т.д. Именно этим аудитом были пойманы почти все баги ниже. Запуск: `node audit.js`, ожидаемый результат — «провалено: 0».

## Хронология: что сделано в этой сессии

### 1. LED и стыки — разбор жалобы «неудобно»
Пользователь пожаловался, что настройка LED-ленты и профилей на стыках разбросана по трём местам формы. Предложил варианты через интерактивный выбор (`ask_user_input_v0`), пользователь выбрал 3 из 4:
- **Клик по краю/шву на схеме** — открывает всплывающее меню (тот же паттерн, что уже был у выбора материала заполнения проёма). Написаны `menuShell`/`menuBtn` — общие хелперы для всех последующих меню.
- **LED на продольных стыках** — раньше подсветка была только у поперечных швов и краёв; добавлено `w.jointsVLed` (позже эволюционировало в более общую систему, см. п.6).
- **Свести LED-настройки в один раздел** — появился раздел «05 LED» в сайдбаре (края стены + список стыков + сводка по ленте/БП), вместо трёх разрозненных мест.

Попутно найден и исправлен **скрытый баг**: клик (без перетаскивания) по автоматическому поперечному стыку тут же превращал его в ручной (эффект был виден только по смене сплошной линии на пунктирную) — почему? — `pointerdown`-обработчик создавал запись в `seamsU` эагерно, ещё до того, как понятно, будет ли drag или просто клик. Исправлено: создание записи отложено до реального движения мыши либо до явного действия в новом меню.

### 2. Баг «детали сами возвращаются на место» после долгой ручной раскладки
Пользователь пожаловался (сначала подозревая «нехватку памяти»), что при длинной серии ручных перетаскиваний на карте раскроя в какой-то момент несколько деталей разом откатываются на старые места без видимой причины.

**Диагностика заняла несколько шагов:**
- Написан синтетический стресс-тест (200 случайных валидных перетаскиваний подряд, без UI) — нашёл 2 «неожиданных отката».
- Причина №1: `applyManual` разрешал ручные правки **в порядке вставки в объект** — ранняя правка проверялась на пересечения только с уже обработанными (по порядку) правками, не со всеми. После многих операций это давало ложный конфликт.
  → Переписано на **итеративное разрешение неподвижной точки**: сначала строятся целевые прямоугольники всех правок, потом по кругу выкидываются конфликтующие, пока не останется устойчивый набор.
- Причина №2 (найдена тем же тестом уже после первого фикса): при конфликте выгонялась **более старая** правка вместо той, что пользователь **только что тронул** — обратный порядок приоритета.
  → Исправлено на уровне записи: каждая запись в `manualMoves` при изменении **удаляется и вставляется заново** (`delete` + set), так что порядок ключей объекта всегда отражает «кто последний трогал» — и именно эта, самая свежая, уступает при конфликте.
- Финальная проверка: 200 синтетических шагов и отдельно 150 шагов через **настоящие события мыши** в headless-браузере (JSDOM) — 0 неожиданных откатов в обоих случаях.

### 3. «Верстак» (временное хранилище деталей)
Запрошена зона над картой раскроя — перетащить деталь туда, чтобы освободить место, покрутить её там, вернуть обратно.

- Данные: `manualMoves.shelf` — массив `{pool, uid, rot}`.
- `applyManual` расширен: деталь на верстаке убирается со всех листов; если это панель с вырезом под проём и в вырезе сидят «из выреза» откосы — они **автоматически едут на верстак вместе с родителем**, если у них нет своей отдельной ручной правки.
- UI: зона `#shelf-zone` над картой, drag в обе стороны, кнопка поворота на детали в верстаке (без ограничений по месту — там места по определению достаточно).
- Особенность: эта работа заняла два хода из-за сброса контейнера песочницы посередине (потеряны тестовые файлы, но не сам код в `raskroy.html` — он восстанавливался из уже выложенного файла).

### 4. Кнопка поворота — два раунда починки
**Раунд 1.** Скриншот показал, что у узких деталей откоса (200 мм полоски) кнопки поворота вообще нет. Причина: порог видимости иконки требовал **обеих** сторон детали ≥ ~240 мм. Исправлено — размер иконки стал адаптивным к размеру детали, с нижним порогом читаемости. Заодно добавлена **геометрическая проверка возможности** поворота (развёрнутая деталь должна физически поместиться хоть на один лист) — иначе кнопка обещала то, что при клике всегда отклонялось. Отдельно — для деталей «из выреза» (сидят в чужом гнезде вместе с соседями) кнопка теперь скрыта совсем: развёрнутая версия почти никогда туда не попадает, а кнопка, которая всегда отказывает, хуже её отсутствия.

**Раунд 2.** После раунда 1 кнопка появилась, но клик всё равно иногда не срабатывал. Причина: старый алгоритм поиска места пробовал только 4 фиксированные позиции (исходное место + 3 угла от него) — если соседи блокируют все четыре, а свободное место реально есть в другой части листа, поворот отклонялся зря. Переписан на полноценный поиск: углы всех свободных зон листа + края соседей с отступом на пропил, с выбором ближайшего к исходному месту валидного варианта. Проверено сравнением с честным брутфорсом (перебор сетки 10 мм по всему листу) на 300 случайных сценариях — 0 расхождений.

### 5. Per-segment режим стыков (соединитель / встык / LED)
Запрос: каждый **отрезок** стыка (не весь стык от пола до потолка) должен настраиваться независимо — если проём разрывает шов на две части, у них могут быть разные режимы.

- `jointSegKey(kind,pos,segStart)` / `jointSegMode(w,G,kind,pos,segStart)` — ключ и резолвер режима по отрезку, с легаси-фоллбеком на старые поля (`jointsVLed`, `seamsU[].led`) для обратной совместимости.
- `w.jointModes` — объект `{ключ: 'cap'|'butt'|'led'}`.
- Меню на схеме (клик по отрезку) и сайдбар (select на каждый отрезок в разделе LED) — три варианта: Соединитель / Встык (без профиля) / LED-соединитель.
- Работает симметрично для продольных и поперечных стыков, в обеих ориентациях раскладки (вертикальной и горизонтальной — там оси физически меняются местами, учтено явно через `crossIsLR`).

### 6. Откосы: Г-образный / встык / изгиб панели
Запрос (по аналогии с п.5): стыки по контуру проёма — тоже три варианта, но других: встык (без профиля) / Г-образный угол (старое поведение) / **изгиб панели** (новая концепция — панель стены сама заходит в глубину проёма, отдельной детали откоса не нужно).

Это оказалось самым большим и самым рискованным куском работы в сессии.

**Изгиб — два независимых механизма:**

- **«Соседняя деталь»** (для случая, когда край проёма совпадает с границей полосы): соседняя полоса физически расширяется на глубину откоса, отдельная деталь откоса для этой стороны не режется.
- **«Недорез»** (для случая, когда проём стоит в середине детали, не по границе полосы — самый частый случай в реальных проектах): в вырезе окна **специально оставляется запас** по одной стороне равный глубине откоса — не дорезается до конца, — и этот запас загибается внутрь. Материал берётся не снаружи, а из того, что иначе стало бы обрезком.

**Правило конфликта** (подтверждено пользователем): изгибать можно одну сторону или противоположную пару (лево+право, верх+низ) — но не две смежные стороны одного угла одновременно, там физически не хватит материала на двоих. При конфликте побеждает «через полосу», проигравшая сторона откатывается на Г-образный угол с объяснением в заметках.

**Найденные и исправленные баги** (все — через 12 000-сценарийный аудит с рандомизированными режимами откосов, не руками):

1. Кусок мог оказаться длиннее листа / шире материала — добавлена проверка вместимости перед применением изгиба, откат на Г-образный при неудаче.
2. Конфликт смежных сторон не ловился, если одна сторона уже прошла через «соседнюю деталь», а другая заходит через «недорез» — проверка конфликта перенесена **до** попытки любого механизма (по самому запросу пользователя, не по факту успеха).
3. Широкий проём, полностью перекрывающий полосу насквозь (там просто дыра, ноль материала) — верх/низ через такую полосу физически не загнуть; раньше часть проёма могла остаться без покрытия молча. Теперь такая сторона целиком откатывается.
4. Вырез уже глубины отгиба (частично задетая полоса) — вычитание давало отрицательный размер детали. Добавлена проверка «у самого выреза должно быть достаточно размера», а не только запаса вокруг него.
5. У двери не бывает нижнего откоса вообще (порог уходит в пол) — но изгиб пытался туда что-то загнуть. Исключено явно, той же логикой, что уже исключала обычную деталь откоса «низ» у дверей.

Каждый баг находился заново после предыдущего фикса — цикл «правка → полный аудит → новый провал в другом месте → диагностика на точном дампе сцены → фикс → аудит» повторялся 4 раза подряд. Итог: 12 000 сценариев, 1,3+ млн проверок, 0 провалов.

### 7. Визуальный индикатор изгиба на карте раскроя
Пользователь спросил «где это показано на раскрое» — оказалось, что обещанный визуальный признак (2 сессии назад) я не довёл до конца, построил только контур на схеме стены, но не на карте раскроя. Признание и исправление:

- `c.orig` — снимок исходных (до сжатия) границ выреза, делается один раз при первом сгибе.
- На карте раскроя: сжатый вырез (уже было) + **янтарная зона с диагональной штриховкой** между исходной и сжатой границей + пунктирная линия сгиба + подпись «загиб, N мм».
- Легенда карты дополнена строкой.
- Пользователь повторно прислал те же скриншоты (без клапана) — оказалось, смотрел старую вкладку/файл. Перепроверено на точных числах из скриншота напрямую через ядро — фикс подтверждён рабочим.

### 8. Откос «Нет» и его два подварианта
Пользователь: иногда откос не нужен вообще (пример — подоконник вместо нижнего откоса окна). Добавлен 4-й режим — сначала как единое «Нет — без отделки» (ни детали, ни профиля).

Затем уточнение: «на стыке всё равно может понадобиться Г-образный профиль или LED, даже без отделки откоса» — то есть **материал** (нужен ли откос) и **профиль на голом торце панели** (даже без откоса) — два разных решения. Переделано на 6 опций в двух группах:

- **С материалом откоса:** Г-образный угол / Встык / Изгиб панели (без изменений).
- **Без откоса (напр. подоконник):** Открытый край без профиля / Заглушка на краю панели / LED-профиль на краю панели.

«Заглушка на краю» уходит в ту же строку сметы, что уже использовалась для проёмов без отделки откоса вообще («Заглушка · торцы у проёмов без откосов») — переиспользован существующий бакет, не плодилась новая категория для физически того же профиля. LED уходит в общий `ledstart`.

### 9. Чистка формы: убрано поле «Отметка 1-го попер. стыка»
Пользователь: поле неудобное, раньше была кнопка добавления стыков — верните её на прежнее удобное место. Сделано:

- Поле `rowH` (отметка первого автоматического стыка) убрано из UI раздела «Объект» полностью. Данные (`w.rowH`) не удалены из модели — старые сохранённые проекты с ненулевым `rowH` **продолжают вести себя как раньше** (значение читается только из данных, форма его больше не пишет и не показывает).
- Кнопка «+ добавить стык» и список ручных поперечных стыков **переехали обратно** в раздел «Объект» (были туда добавлены изначально, потом в одной из более ранних сессий уехали в раздел LED при его консолидации — оказалось неудобно, т.к. это геометрия стены, а не свет).
- Раздел LED сохранил только: края стены, продольные стыки, сводку по ленте — и ссылку-подсказку «поперечные стыки — в разделе Объект».

## Рецепт пересборки core.js (для продолжения тестирования в Cowork)

```python
import io
s = io.open('raskroy.html', encoding='utf-8').read()
js = s[s.index('<script>')+8 : s.rindex('</script>')]
names = ['subRanges','subIn','buildLayout','packSheets','packSheetsCols','buildOtkosParts',
         'packOtkos','nestProfile','subtractRects','holeRects','rotateCuts','applyManual','wallS',
         'jointSegMode','computeProject','compute']
def grab(n):
    i = js.index('function '+n+'('); d=0; st=False; j=i
    while j < len(js):
        c = js[j]
        if c=='{': d+=1; st=True
        elif c=='}':
            d-=1
            if st and d==0: return js[i:j+1]
        j += 1
funcs = '\n\n'.join(grab(n) for n in names)
```
